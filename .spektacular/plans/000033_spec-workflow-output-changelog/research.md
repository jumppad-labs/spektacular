# Research: spec-workflow-output-changelog

## Alternatives considered and rejected

1. **Extend the existing repo-root `CHANGELOG.md` to also carry the durable record.**
   Rejected — explicitly forbidden by the spec's constraints (`.spektacular/specs/000033_spec-workflow-output-changelog.md:34`: "Must not replace or repurpose research.md or plan.md" and the overall framing that this is "a distinct, additional, retrospective artifact"). Also structurally wrong: `CHANGELOG.md` entries are deliberately terse, 2-4 sentence, no-implementation-detail release notes (`templates/steps/implement/08-update_repo_changelog.md:14`) — the opposite of "dense enough for an agent to extract structured facts" required by the spec (`000033:20-21`).

2. **Extend the plan's inline `## Changelog` section (in `plan.md`) to also serve as the durable record.**
   Rejected — that section is explicitly the "phase-by-phase implementation audit log" (`templates/steps/implement/07-update_changelog.md:3`, confirmed by prior plan `.spektacular/plans/000015_implementation/plan.md:23`), written once per phase, developer-facing, and living inside the plan store which is a planning-internal document per the spec's own constraint. It's also not self-contained — it assumes the reader has `plan.md`'s other sections (Overview, Requirements) for context, whereas the new record must stand alone (`000033:17-18`).

3. **A single growing changelog file (append-only, one file for the whole project) rather than one file per feature.**
   Rejected in favor of per-feature files. The spec's acceptance criteria require retrieving "a specific feature's record... individually, without needing to read or search the entire history" (`000033:53-54`). A single growing file would require either an index/manifest (no precedent anywhere in the codebase — confirmed by search, see Files examined) or linear scanning, whereas per-feature files reuse the codebase's universal convention of filename-as-identifier (see `plan file read <name>/plan.md`, `spec file read <name>.md`) for O(1) retrieval with zero new indexing code.

4. **Introduce a manifest/index file (e.g. `changelog/index.json`) alongside per-feature records.**
   Rejected as unnecessary for this spec's requirements. No existing store (spec, plan, knowledge) in this codebase uses a manifest — `store.List` is a plain `os.ReadDir` (`internal/store/store.go:125-142`) and retrieval is uniformly filename = identifier. Introducing a manifest here would be the first instance of that pattern in the codebase, adding a new failure mode (index/file drift) for no requirement that isn't already satisfied by "one file per feature, named after the feature". If a future spec needs cross-record querying beyond `store.Search`, a manifest can be added later without breaking the per-file convention.

5. **Have the new step live inside the `internal/steps/plan` package (attached to the plan workflow) instead of `internal/steps/implement`.**
   Rejected — the spec requires the record to capture "what was actually done... even where the actual implementation diverged from the original plan" (`000033:14-15`) and to fire "when a unit of work is fully implemented" (`000033:11-12`). Only the implement workflow has this information (completed phases, the accumulated inline changelog, verification/test results) — the plan workflow runs entirely before any code exists.

6. **Store the changelog content in `workflow.Data` and have a Go-code callback assemble the record programmatically from stored fields (files changed, deviations, etc. accumulated across steps).**
   Rejected — confirmed no implement step callback ever calls `data.Set(...)` (grepped `internal/steps/implement/*.go`, zero matches outside tests); the only key ever in `Data` is `"name"` (`cmd/implement.go:141`). Retrofitting every prior step to accumulate structured data into `Data` would be a much larger, invasive change and cuts against the established pattern where all step callbacks are "render a template, let the agent do the file I/O" (`internal/workflow/workflow.go:39` signature; in practice for implement steps, nothing is stored in `Data` at all — all substance lives in on-disk artifacts the agent reads live). The new step instead follows the exact same shape as the existing `update_changelog`/`update_repo_changelog`/`test_plan` steps: a template instructs the agent to read `plan.md` live via the CLI and author the record's prose itself.

7. **Fold changelog-record generation into the existing `finished` step, or make it config-gated/optional.**
   Both presented to the user during the architecture step and explicitly rejected. Folding in was rejected because `finished` is today a pure, file-I/O-free reporting step (`templates/steps/implement/10-finished.md:1-19`), and conflating "author a durable artifact" into it blurs that single responsibility. Config-gating was rejected because nothing in the spec calls for opt-out — "without requiring the user to manually write it" (`000033:12`) reads as always-on — and gating would add a config branch plus conditional FSM wiring for a case nobody asked for.

## Chosen approach — evidence

**New store kind: `changelog`, one file per feature, config-driven directory, reusing the existing `store.Store` + `newStoreFileCmd` machinery unchanged.**

- `internal/store/store.go:37-55` — the `Store` interface is already fully generic (Read/Write/Delete/List/Exists/Search) and has zero notion of "kind"; a changelog store needs no new store-layer code, only a new root directory, exactly like plan/spec today.
- `cmd/storefile.go:17` (`type storeDirFunc func(config.Config) string`) and `cmd/storefile.go:39-124` (`newStoreFileCmd`) — the entire `file read/write/delete/list` command group is a parametrized factory. `cmd/plan_file.go:8-12` and `cmd/file.go:7-11` show the two-line wiring pattern to add a third: a new `cmd/changelog_file.go` with `changelogCmd.AddCommand(newStoreFileCmd(..., func(c config.Config) string { return c.Changelog.Config.Directory }))`.
- `internal/config/config.go:60-68` (`PlanConfig`/`FilePlanConfig`) — direct struct-clone template for a new `ChangelogConfig`/`FileChangelogConfig` pair; `config.go:89-96` (`Config` struct fields) and `config.go:112-117` (`NewDefault()` population) are the two other edit points; `config.go:187-195` (`PlanConfig.Validate()`) is the validate-method template, wired in at `config.go:159`.
- `internal/store/store.go:102-111` — `Write` auto-`MkdirAll`s parent directories, so the changelog root needs no explicit scaffolding in `cmd/init.go` (`project.Init` at `cmd/init.go:32` does not need a new call) — it is created lazily on first write, consistent with how plan/spec directories behave today (not separately scaffolded in `init.go`, confirmed no `MkdirAll`/`DefaultSpecDir`/`DefaultPlanDir` reference exists in `cmd/init.go`).
- `internal/store/search.go:39-40` — `Store.Search` walks the entire store root category-agnostically; since specs, plans, and (new) changelog all live under `.spektacular/`, once a `changelog` scope/root is added it is automatically full-text searchable via the existing `knowledge search`-style infra with zero new search code, giving the spec's "downstream process can retrieve" requirement (`000033:26-27`) a second, complementary retrieval path (search) beyond direct filename lookup.

**New implement-workflow step inserted between `test_plan` and `finished`, following the `test_plan` step's exact shape (read plan.md live via CLI, agent authors prose, stage to `.spektacular/tmp/`, commit via `<kind> file write`, then advance).**

- `internal/steps/implement/steps.go:16-30` — the full FSM step list; insertion point is changing `{Name: "finished", Src: []string{"test_plan"}, ...}` (`steps.go:28`) to `{Name: "finished", Src: []string{"update_feature_changelog"}, ...}` and inserting `{Name: "update_feature_changelog", Src: []string{"test_plan"}, Dst: "update_feature_changelog", Callback: updateFeatureChangelog()}` before it.
- `internal/steps/implement/steps.go:125-129` (`testPlan()`) — the closest sibling step: single `writeStep` call, runs once (not looped), writes one artifact to the plan/feature store via agent-driven CLI calls, no `Data` mutation. `updateFeatureChangelog()` is written identically in shape.
- `templates/steps/implement/09-test_plan.md` (full content read) — direct template model: Step 1 gathers source material by reading `plan.md` live (`{{config.command}} plan file read {{plan_name}}/plan.md`), Step 2 has the agent author prose grounded in the *actual* implementation, Step 3 stages via `Write` to `.spektacular/tmp/`, commits via `{{config.command}} plan file write <name>/test-plan.md --from ...`, then `rm`s the scratch file, includes a STOP-on-mismatch guard, and ends with the standard Advance + context.md-refresh footer every step template carries. The new template mirrors this exactly but targets `{{config.command}} changelog file write {{plan_name}}.md --from .spektacular/tmp/changelog_record.md`.
- `internal/steps/implement/strategy.go:37-49` (`PathVars`) — needs new computed vars `changelog_path` and `spec_path`, built the same way as `plan_path`/`context_path`/`research_path` (`filepath.Join(storeRoot, ...)`), plus a new `ChangelogFilePath(dir, name string) string` helper mirroring `PlanFilePath`/`ContextFilePath` (`strategy.go:13-27`). `spec_path` clones the plan workflow's own existing approach (`internal/steps/plan/strategy.go:22`: `specPath := filepath.Join(storeRoot, s.specDir, instanceName+".md")`) — the implement workflow has no `spec_path` today, and this reuses a convention the plan workflow already proves works ("plan slug equals spec filename stem"), rather than inventing a new lookup. Confirmed: `workflow.Config` (`internal/workflow/workflow.go:17-27`) has only `Command`, `Kind`, `DryRun`, `SpecDir`, `PlanDir` — a new `ChangelogDir string` field must be added to this struct, then sourced into it at `cmd/implement.go:137` and `cmd/implement.go:204` from a new `config.Config.Changelog.Config.Directory`.
- `templates/steps/implement/07-update_changelog.md:9-11` and `:37-42` — shows the exact "read via CLI, ensure section/file exists, stage to scratch, commit via `<kind> file write`" idiom the new template's Step 1/3 copies, including the "never read/write with Read/Write/Edit tools directly on store documents" rule (`07-update_changelog.md:5`) which extends to the new changelog store the same way.
- `templates/steps/implement/10-finished.md:1-19` — the terminal step's "Summary" bullets gain one more line noting the changelog record location, mirroring the existing bullet about the repo `CHANGELOG.md` location (`10-finished.md:9`), so the agent reports it to the user per the "What to do next" section.

**Record content shape:** one Markdown file per feature (e.g. `.spektacular/changelog/{{plan_name}}.md`), authored by the agent (not templated boilerplate) from: the spec's Overview/Requirements (why it matters — self-contained framing), the plan's `## Changelog` section already accumulated during `update_changelog` (what was actually built, phase by phase, including recorded deviations — this is the existing, only place "actual vs. planned divergence" is already captured, per `07-update_changelog.md:20-22`'s `**Deviations**` field), and the files-changed lists already recorded per phase. This directly satisfies acceptance criteria "Record reflects actual outcome, not the original plan" (`000033:41-42`) by construction — the source material already privileges actual-outcome over planned-outcome.
