# Research: 000034_spec-plan-implement-reconciliation

## Alternatives considered and rejected

- **New standalone `reconcile` workflow/command.** Rejected by the spec's own constraint ("Must operate within the existing plan and implement workflows — this is additive verification within those workflows, not a new standalone workflow or command"). Would also duplicate FSM/state-machine plumbing (`internal/workflow/`) that already exists.
- **Pre-check as a Go-level hard gate (fail the callback, refuse to advance) instead of a template-driven STOP-and-ask.** Rejected: spec Non-Goal explicitly rules out "Blocking or hard-failing the workflow on a coverage gap — the check surfaces the gap and asks the user, it does not make the workflow refuse to proceed." All existing gates in this codebase (`01-read_plan.md` Step 2/3, `14-verification.md`) are template-driven STOP-and-ask, not Go-level `Cancel(err)` — consistent with this constraint. `internal/workflow/workflow.go`'s `before_<event>` + `Cancel(err)` mechanism exists but is used for structural veto (e.g. missing plan file), not for a resolvable-by-user gap.
- **New Go-level branching primitive (an explicit "decision" field in `StepConfig`) for the "update plan vs. accept gap as descoped" choice.** Rejected: no such primitive exists anywhere in the FSM (`internal/workflow/workflow.go`); all existing branches (`update_changelog` → `analyze` or `update_repo_changelog`, see `templates/steps/implement/07-update_changelog.md:44-64`) are encoded purely as multi-source `Src` edges plus template instructions telling the agent which `goto` to call. Introducing a new mechanism here would be inconsistent with the codebase's established pattern and unnecessary — the multi-source-edge pattern already supports arbitrary branching.
- **Re-deriving "what was built" from a fresh diff/git log at post-implementation check time.** Rejected per the spec's own Technical Approach suggestion and confirmed by prior art: the plan's inline `## Changelog` section (`templates/steps/implement/07-update_changelog.md`) already accumulates a phase-by-phase implementation record (What was done / Deviations / Files changed / Discoveries) purpose-built for exactly this kind of reconciliation, and `10-update_feature_changelog.md` already treats it as the authoritative source over "the original plan text." Reusing it avoids re-deriving anything and stays consistent with existing conventions.
- **Folding the post-implementation spec-checkoff entirely into the Go `finished()` callback instead of a template-driven step.** Considered viable (there's Go-side precedent: `plan/steps.go:277-299`'s `finished()` already reads store state and injects a conditional `extra["plan_incomplete"]` flag before rendering). But rejected as the *primary* mechanism because checking off spec checkboxes requires judgment (does the phase-entry evidence actually satisfy this specific acceptance criterion's wording?) that belongs in agent-driven template instructions, not deterministic Go code — consistent with how `10-update_feature_changelog.md` already delegates similar judgment-laden authoring to the agent rather than Go. Go-side `extra` flags remain the right tool for *mechanical* signals (e.g. "spec file not found" or "no Requirements/Acceptance Criteria headings"), not for the coverage judgment itself.
- **Running the pre-implementation coverage check in both plan's `verification` step and implement's `read_plan` step.** This was this document's own original proposal during discovery (see "Chosen approach" below for the full reasoning it was based on). Explicitly rejected by the user during the architecture step in favor of a single check point in `read_plan` only: `read_plan` runs on every `implement` invocation regardless of whether the plan was freshly generated or hand-edited afterward, so a single check catches both cases without the cost of maintaining duplicate comparison logic in two workflow packages for no additional guarantee.

## Chosen approach — evidence

**Pre-implementation coverage check — lands solely in the `implement` workflow's existing `read_plan` step. LOCKED by explicit user decision during the architecture step, superseding this section's original dual-location proposal (see note below).**
- `internal/steps/implement/steps.go:19` (`read_plan`): `templates/steps/implement/01-read_plan.md` is already explicitly documented as "the validation and drift gate for the implement workflow. Nothing else runs until it passes" (line 3) and already ends with a STOP-and-three-option prompt pattern (lines 53-59) that is the exact UX shape needed for a coverage gap ("update the plan" / "accept the gap as descoped" — a 2-option variant of the existing 3-option pattern). `implement`'s strategy (`internal/steps/implement/strategy.go:52,61`) already computes `spec_path` for every step, so no new plumbing is needed.
- This check runs at the single moment implementation is about to start against whatever the plan currently says — whether freshly generated by the `plan` workflow or hand-edited afterward (exactly the 000032 failure mode: "This stops the user changing the plan to divert from the spec's goal" — exact user phrasing in `.spektacular/context.md`). A single check point, run every time `implement` starts, covers both cases.
- **Original proposal during discovery** (superseded): this section originally proposed running the same check in *two* places — plan's `14-verification.md` (`internal/steps/plan/steps.go:44`, already a pure gate with `spec_path` available via `internal/steps/plan/strategy.go:22,30`) as well as `implement`'s `read_plan`, reasoning that the plan-side check would catch a gap at plan-creation time before a stale plan even reaches the store. **The user explicitly rejected the dual-location option during the architecture step** in favor of a single check in `read_plan` only, judging that maintaining the same comparison logic in two workflows for a single-check guarantee was unneeded complexity — a fresh or hand-edited plan is caught either way, since `read_plan` runs on every `implement` invocation regardless of how the plan came to look the way it does. The `plan` workflow package (`internal/steps/plan/`) is therefore **not modified** by this plan at all. This supersedes the "don't re-flag an accepted gap... small Go-side `data.Set`/`data.Get` flag" idea below — the accepted-gap record lives in the plan document itself (see Open Assumptions), not in `state.json`.

**Post-implementation reconciliation — folds into a new step inserted between `update_feature_changelog` and `finished`; final report content extends `11-finished.md`.**
- `internal/steps/implement/steps.go:28-29` — current tail: `update_feature_changelog → finished`. `updateFeatureChangelog()` (`steps.go:136-140`) already reads spec + plan changelog to author the durable changelog record — this is the exact same source material (spec Requirements/Acceptance Criteria + plan's `## Changelog` phase entries) the reconciliation check needs, read in the immediately-preceding step.
- `templates/steps/implement/10-update_feature_changelog.md:5-14` — Step 1 "Gather source material" already does `spec file read {{plan_name}}.md` + `plan file read {{plan_name}}/plan.md`, and explicitly says to lean on the plan's accumulated `{{changelog_section_name}}` phase entries "rather than re-deriving anything from the original plan text" — directly reusable as the comparison source per the spec's Technical Approach suggestion.
- `templates/steps/implement/11-finished.md:1-21` — the terminal step is pure template interpolation with no store reads currently (`internal/steps/implement/steps.go:142-146`, `finished()` calls `writeStep` with `extra=nil`). Its "What to do next" section (lines 12-19) is exactly where "the summary presented to the user must include the specification's completion status alongside the usual summary of changes" (spec constraint, verbatim) needs to land.
- `internal/steps/plan/steps.go:277-299` — `finished()` in the **plan** workflow is the concrete precedent for computing a conditional flag (`plan_incomplete`) in Go and interpolating it into the terminal template's rendering — the mechanical part of "was the spec file successfully read and does it have the expected headings" can follow this exact shape for the **implement** `finished()` if desired, while the judgment part (which checkboxes are satisfied) still needs to happen earlier, in an agent-driven step, because only an agent can judge semantic satisfaction.
- **Decision: introduce one new step, `reconcile_spec`, with `Src: []string{"update_feature_changelog"}, Dst: "reconcile_spec"`, and retarget `finished`'s `Src` to `["reconcile_spec"]`.** This step (a) reads the spec (already-fetched by the preceding step, but re-read here through the CLI per the "always re-read through the CLI, never hold state across steps" convention visible throughout — e.g. `07-update_changelog.md:9,46` re-reads plan.md twice in one step rather than reusing an earlier read), (b) reads the plan's `## Changelog` phase entries, (c) for each Requirements/Acceptance-Criteria checkbox, judges satisfied/unsatisfied/descoped-accepted-earlier, (d) stages and commits an updated spec file via `spec file write` (checking off satisfied boxes — mirrors the stage-to-`.spektacular/tmp/`-then-write-then-`rm` pattern used everywhere else, e.g. `07-update_changelog.md:37-42`), (e) the spec file itself, freshly rewritten, is the durable record of the outcome — no new data-threading between `reconcile_spec` and `finished` is required; `finished` just re-reads the spec (already has `spec_path`) the same way it already re-reads `plan_path`/`changelog_path`.
- Naming precedent: existing step names are all `snake_case` verb-first or verb-phrase (`update_plan`, `update_changelog`, `update_repo_changelog`, `test_plan`, `update_feature_changelog`) — `reconcile_spec` matches this convention. Corresponding template file continues the numeric-prefix convention: `11-reconcile_spec.md`, with the renumbered `finished` step becoming `12-finished.md` (the `10-update_feature_changelog.md`→`11-finished.md` rename in the prior changelog feature, done via `git mv` per the prior-plans research, is the direct precedent for this renumbering — a "free, non-behavioral implementer choice").

## Open assumptions

- **Assumed:** the plan-name-equals-spec-filename-stem convention (`spec_path` derived as `{specDir}/{instanceName}.md` in `implement/strategy.go:52`) always holds for any plan this feature will operate on. There is no stored/validated link between a plan and its originating spec. **If this turns out wrong** (a plan whose name doesn't match its spec's filename) — the coverage check would silently read the wrong spec or a missing file. The pre-check step must treat "spec file not found at the conventional path" as a STOP-and-ask condition (mirroring `10-update_feature_changelog.md`'s existing STOP-on-mismatch for exactly this scenario), not a silent skip. This should hold given the codebase's existing behavior already depends on this convention (e.g. `updateFeatureChangelog` already assumes it), but the implement workflow must verify, not assume, at runtime.
- **Settled (was an open assumption during discovery, locked during architecture):** "don't re-flag an already-accepted gap" (acceptance criterion: "an accepted gap is not flagged again for the same plan") is satisfied by writing the user's acceptance decision into the plan document itself — a `**Descoped requirements**:` list, per the plan's Phase 1.2 — rather than into `state.json`'s `data` field. Confirmed during the architecture step: plans/specs are this codebase's durable, human-visible record of decisions; `state.json`'s `data` field is used elsewhere only for transient per-run values. Written to the plan document, the marker survives a `state.json` reset or a fresh `implement new` run against the same plan later.
- **Assumed:** the post-implementation reconciliation step's judgment ("does this phase's changelog entry actually satisfy this specific acceptance criterion's wording") is inherently agent-driven prose-in-template-instructions, not something a Go callback can determine mechanically (unlike the mechanical "is this section present" checks in `14-verification.md`). This mirrors how `10-update_feature_changelog.md` already delegates similarly judgment-laden authoring to the agent. If implementation finds a more mechanical signal is feasible, that should be flagged and this assumption revisited — but nothing in the codebase today suggests spec-checkbox-satisfaction can be determined without semantic judgment.
- **Settled (locked during architecture, confirmed at milestones/phases):** exactly one new FSM step (`reconcile_spec`) is used on the implement side for the post-check, rather than folding into `update_feature_changelog` directly. Chosen as a separate step because `update_feature_changelog`'s existing job (author a changelog-store record) is already fully scoped and documented, and mixing "write an external changelog record" with "check off boxes in the spec file and decide what's unsatisfied" in one step's instructions would make that step's STOP-on-mismatch conditions harder to reason about (two different failure classes, two different artifacts being written).
