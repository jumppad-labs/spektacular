# Research: 000031_agent-session-debug-log

## Alternatives considered and rejected

1. **Hook `cobra.Command.PersistentPreRunE`/`PersistentPostRunE` to capture each command and its result.**
   Rejected. No such hook exists today (`cmd/*.go` grep for `PersistentPreRun|PersistentPostRun|PreRun|PostRun` → zero hits). Cobra does not run `PostRun` when `RunE` returns an error, so a `PostRun`-based recorder would silently miss every failure response — the exact "non-progress events" class the spec requires captured (spec §Acceptance Criteria "Non-progress events included"). `os.Args[1:]` is already the literal, ground-truth text of "the command the agent issued" and is available in `cmd/root.go`'s `runRoot()` before `rootCmd.Execute()` is even called (`main.go:1-7` → `cmd.Execute()` → `runRoot()`, `cmd/root.go:24-26,33`), with no cobra lifecycle coupling needed.

2. **Edit each of the ~40 individual `output.Write`/`WriteResult` call sites (plus the one outlier at `cmd/skill.go:87-92` that bypasses `output.Write` entirely with a raw `json.MarshalIndent`+`Fprintln`) to also emit to a recorder.**
   Rejected. Exactly the anti-pattern plan `000030_agent-actionable-errors` (this repo's most recent, directly analogous plan) explicitly avoided for the error-formatting problem: `plan.md`'s Architecture & Design Decisions chose "one choke point... rather than fixing formatting at each of the ~40 existing error-return sites individually." Editing 40+ sites is larger blast radius, more places to keep in sync, and can't reach `skillListCmd`'s raw bypass without also special-casing it. A writer-level tap covers all ~40 sites plus the outlier for free (see Chosen approach).

3. **Derive "did this command make forward progress" purely from the returned error's type/nilness** (e.g. `nil` = progress, `*output.ErrorResponse` = no progress).
   Rejected as insufficient — proven wrong by a real, already-documented gotcha. `Workflow.Goto(name)` where `name == the current step` takes a silent no-op path (`internal/workflow/workflow.go` `renderStep`, per research agent): it re-invokes the step's callback to re-emit the instruction, fires no FSM event, never calls `saveState`, and returns `nil` — indistinguishable in shape from a genuine advance. This is independently documented at `.spektacular/knowledge/gotchas/goto-to-current-step-is-a-silent-noop.md`, which explicitly flags it as worth checking "when diagnosing an agent stuck re-reading the same instruction repeatedly" — i.e. precisely the scenario motivating this feature (spec's Success Metrics: "an agent got stuck... identify the point things went wrong"). Error type alone would misreport this no-op as a successful advance.

4. **A new session-identification mechanism supplied by the calling agent/harness** (e.g. requiring the agent to pass a `--session-id` flag, or rely on an env var such as `SPEKTACULAR_SESSION_ID` set once per conversation).
   Rejected. No such convention exists in this codebase (`grep` for `uuid|session_id|SessionID` — no hits outside unrelated Dagger-generated code). Requiring the caller to pass or export anything violates "Non-invasive" (spec requirement) — it would change what the agent must do to invoke the tool — and env vars are not reliably persisted across the separate OS processes each CLI invocation runs as (this codebase is invoked once per command, a fresh process every time — confirmed by `main.go`'s trivial `func main() { cmd.Execute() }` and no `os.Args`/session plumbing anywhere). An auto-derived, idle-gap-bounded session id (see Chosen approach) requires zero cooperation from the caller.

5. **A new external store (SQLite, embedded KV store, etc.) for the record.**
   Rejected outright by the spec's own constraint: "must not introduce a new external service, background process, or additional runtime dependency." Append-only JSON Lines on local disk needs no new dependency and is sufficient for the spec's actual requirements (sequential reconstruction after the fact; no query/browse UI is in scope — explicitly a Non-Goal).

6. **One record file per session** (file name keyed by session id) rather than one continuously-appended file tagged per-line with a session id.
   Rejected in favor of the single-file approach: per-session files require a naming/discovery/cleanup story the spec explicitly puts out of scope ("A retention, rotation, or cleanup policy for old records is out of scope"). A single append-only file with a `session_id` field on every line needs no such story — a reader groups/filters lines by `session_id` (trivial even with `grep`/`jq`), which already satisfies "Session isolation" (Acceptance Criteria: "each can be identified as belonging to its own session and is not intermingled with the other's events") without adding file-management surface.

7. **Reuse `.spektacular/tmp/` (rather than `.spektacular/debug/`) as the record's location.**
   Considered, not rejected outright — both are already gitignored (root `.gitignore`: `.spektacular/debug/` and `.spektacular/tmp/`; `.spektacular/.gitignore` also covers `tmp/`). `debug/` is the stronger fit: its own root-`.gitignore` comment already reads "# Spektacular debug output", it already exists as a directory precedent (currently holding stale, unrelated JSONL transcripts from a dead `internal/runner`-era harness, dated 2026-03-04 to 2026-03-06 — confirmed nothing in current `cmd/`/`internal/` writes there today), and `tmp/` is used elsewhere in this codebase's own skill conventions (`.spektacular/tmp/`) for ephemeral staging of content being written *through* the store (plan/spec file writes), a different and unrelated purpose from a standing debug record. Chosen: `.spektacular/debug/`.

## Chosen approach — evidence

- **Toggle**: reuse `internal/config.Config.Debug.Enabled` (`internal/config/config.go:39-42`, wired into `Config` at `:92`, defaulted `false` at `:100-104`). It already round-trips through `.spektacular/config.yaml` (`FromYAMLFile`/`ToYAMLFile`, `config.go:135-152,240-250`) and is already covered by existing tests (`internal/config/config_test.go:15,79`). It has **zero current read-sites** anywhere in `cmd/`/`internal/` (confirmed by repo-wide grep) — wiring it up satisfies the spec's Technical Approach ("prefer reusing any existing diagnostic/debug toggle mechanism... rather than introducing a new, separate way to turn this on") exactly, and this repo's own checked-in `.spektacular/config.yaml` already has `debug: enabled: true` set, suggesting this reuse was anticipated. `runRoot()` (`cmd/root.go:33-40`) already has direct access to call `loadConfig()` (`cmd/root.go:63-72`) itself, independent of each subcommand's own `loadConfig()` call — so reading the toggle needs no plumbing through `workflow.Config`/`Data` or any of the ~40 command handlers.

- **Command+response interception point**: `runRoot()` (`cmd/root.go:33-40`) is the one function every invocation passes through in both directions. `os.Args[1:]` captures "the command the agent issued" verbatim, read before `rootCmd.Execute()`. For the response, `rootCmd.SetOut(io.MultiWriter(originalOut, recorderBuf))` — set once, conditionally, before `Execute()` — tees every byte any of the ~40 `output.Write`/`WriteResult` call sites (`cmd/spec.go`, `cmd/plan.go`, `cmd/implement.go`, `cmd/knowledge.go`, `cmd/skill.go`, `cmd/storefile.go`, all writing to `cmd.OutOrStdout()`) and `output.WriteFailure` (`cmd/root.go:38`) write, *and* the one outlier (`cmd/skill.go:87-92`'s raw `Fprintln`, since it also writes to `cmd.OutOrStdout()`), into the recorder's in-memory buffer — without altering what reaches the real stdout (`io.MultiWriter` writes the same bytes to both). This is provably non-invasive: the real writer receives byte-identical output whether or not the tee is present. No changes to any of the ~40 call sites, `internal/output`, or `internal/workflow` are needed.

- **Outcome/state-change capture**: read `.spektacular/state.json` (path built via `dataDir()`/`stateFilePath()`, `cmd/root.go:76-82`, `cmd/spec.go:99-101`) once immediately before `rootCmd.Execute()` and once immediately after, in `runRoot()`. Diff the relevant fields (`State.CurrentStep`, `State.CompletedSteps`, `State.UpdatedAt` — `internal/workflow` `state.go:14-21`) to derive a `state_changed` signal that is correct even for the silent-no-op case (`Goto` to the current step: alternative 3 above) that a bare error-type check would miss. This directly satisfies the Technical Approach's "capture the outcome of each command... what state (if any) actually changed... so a diagnosing agent can tell a real advance apart from a rejected or no-op one." Reading the file directly (rather than adding a hook inside `internal/workflow`) keeps the whole feature scoped to `cmd/root.go` plus one new small package, mirroring the "single choke point, not many touch points" precedent plan `000030_agent-actionable-errors` established for the adjacent problem (its `plan.md` Architecture & Design Decisions section).

- **Session identity (user-directed)**: rather than minting and separately persisting a new random/idle-gap-derived id, derive `session_id` as a pure function of `.spektacular/state.json`'s existing `Kind` + `Data["name"]` (e.g. `"<kind>:<name>"`) at the moment each command runs — the user's explicit direction was "it has to be linked to the state, when the state name or mode changes." This needs **no new persisted marker file at all**: the id falls straight out of state that already exists and is already read for the before/after diff (see previous bullet), so the same single state.json read serves both purposes. A session boundary occurs exactly when `(Kind, Name)` changes between two consecutive commands — which includes starting a new workflow instance, switching kind, or (deliberately) does *not* occur when the same named instance is resumed after a long real-world gap, since its `(Kind, Name)` is unchanged; that is treated as a continuation of the same session by design (one record spans every attempt at the same instance, which is more useful for a diagnosing agent than fragmenting on wall-clock gaps). Commands issued with no workflow state on disk yet (e.g. a bare `knowledge search` before any `spec new`/`plan new`/`implement new`) fall back to a fixed sentinel session id (proposed: `"no-active-workflow"`) rather than an idle-gap heuristic — flagged as the one remaining open point below.

- **Format**: JSON Lines (one JSON object per completed CLI invocation, newline-delimited, append-only) at `.spektacular/debug/session-log.jsonl`. This directly matches the Technical Approach's "consider one discrete record per captured event" and "consider timestamping each captured event." It is also the same shape already used, independently, by this project's own architecture references for agent/tool transcripts (`.spektacular/knowledge/architecture/bob_json/bob_stream.json`, `.spektacular/knowledge/architecture/example-output/{load-agent,run-plan}.json` — both real JSONL transcripts, one event object per line, each carrying its own `type`/`timestamp`), giving external precedent that a JSONL-of-discrete-typed-events shape is a workable, agent-consumable record format for exactly this kind of "reconstruct what an agent did" use case (`.spektacular/knowledge/architecture/claude-output-spec.md`, `.spektacular/knowledge/architecture/bob-output-spec.md`). Each line carries an explicit monotonically increasing sequence number in addition to a timestamp, so ordering is unambiguous even under coarse timestamp resolution or clock anomalies (spec Acceptance Criteria: "Unambiguous ordering").

## Open assumptions

- **User-confirmed (architecture step):** architecture Option 1 (root-level tee + state diff, all
  in `cmd/root.go` plus one new package) chosen over the two heavier alternatives (cobra
  Persistent-hooks + workflow-engine signal; structured recording inside `internal/output`).
- **User-confirmed (architecture step):** session id is derived from `.spektacular/state.json`'s
  `(Kind, Name)` pair rather than an idle-gap marker file — see Chosen approach above. Remaining
  open point: the exact sentinel session id to use when no state.json exists yet / no workflow has
  ever run in this project (proposed: `"no-active-workflow"`) — low-stakes, an implementation
  default rather than a design fork, does not need further confirmation.
- **User-confirmed (architecture step):** each record stores the full raw response bytes verbatim
  (not a structured subset) — most self-contained, satisfies "reconstructable without the agent's
  memory" and "machine-extractable detail" directly, and avoids needing the recorder to understand
  every response shape (including the `file read` raw-bytes exception and the `skillListCmd`
  outlier).
- **`.spektacular/debug/session-log.jsonl` as the exact file name/path is assumed, not separately
  confirmed with the user.** The directory (`.spektacular/debug/`) is well-evidenced; the specific
  file name within it is a low-stakes implementation choice.
- **Config-load failure handling is assumed to fail open (recording silently disabled), never
  failing the primary command.** Not stated in the spec directly, but required by "Non-invasive"
  (recording must never change the tool's outcome) — if `runRoot()`'s own `loadConfig()` call for
  the toggle errors, the assumption is to treat debug as disabled for that invocation rather than
  surfacing a new failure mode.
- **`state.json` presence is optional and its absence (e.g. for non-workflow commands like
  `knowledge search` before any workflow has ever run) is not an error** — the before/after
  snapshot records "no state file" (and the sentinel session id above), rather than treating a
  missing file as a diff-worthy change or a failure.
