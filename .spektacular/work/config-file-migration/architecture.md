The migration is implemented as an extension to the existing `version check` command (`cmd/version.go`), which already detects version mismatches and prompts users for action. When version check runs, it will detect the old single-file format by checking for the presence of `config.yaml` without a corresponding `repo.yaml` in the `.spektacular/` directory. Upon detection, it returns a structured prompt in its existing output format, explaining that the configuration will be split and backed up.

When the user confirms migration, the system scans the project to suggest appropriate repository metadata values. It examines `README.md` for a description (using the first paragraph), checks for `go.mod` or `package.json` to infer the role (tool vs application), and inspects directory structure for tags. If scanning cannot determine a value, sensible defaults are used: description "Spektacular project", role "application", tags empty array, deployment "manual". The original `config.yaml` is renamed to `config.yaml.old` as a backup, then the new split configuration is written: project-level settings remain in `config.yaml` (using `Config.ToYAMLFile()`), while repository metadata goes into the new `repo.yaml` (using `RepoConfig.ToYAMLFile()`).

This approach beats alternatives because it requires no separate migration command (reducing friction), integrates naturally with the existing version check workflow that users already run after upgrades, and reuses proven patterns from `cmd/init.go` for writing both config files. The migration is atomic: if any step fails after the backup is created, both new files are removed and the backup is restored, ensuring users never end up in a broken state.

For detailed analysis of rejected alternatives (separate migration command, automatic migration without prompt, preview-then-confirm flow), see `research.md#alternatives-considered-and-rejected`.
