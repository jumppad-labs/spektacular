# Context: 000031_agent-session-debug-log

## Current State Analysis

Spektacular is a single Go binary (`main.go:1-7` → `cmd.Execute()`) driven entirely by cobra subcommands issuing and receiving JSON, one command per OS process. `cmd/root.go:33-40`'s `runRoot()` (added by plan `000030_agent-actionable-errors`'s Phase 1.2, merged same-day as this plan's discovery) is already the single choke point every command's outcome passes through: it calls `rootCmd.Execute()`, and on error formats a shared `ErrorResponse` via `internal/output.WriteFailure` (`internal/output/writer.go:88-90`) onto the same stdout stream a success already used, silencing cobra's own default error/usage printer (`rootCmd.SilenceErrors`/`SilenceUsage`, `cmd/root.go:100-101`). Success responses, however, are **not** centralized the same way — each of ~40 call sites across `cmd/spec.go`, `cmd/plan.go`, `cmd/implement.go`, `cmd/knowledge.go`, `cmd/skill.go`, `cmd/storefile.go` calls `internal/output.Write`/`(*Writer).WriteResult` directly against `cmd.OutOrStdout()`, with one outlier (`cmd/skill.go:87-92`, `skillListCmd`'s `RunE`) bypassing `output.Write` entirely with a raw `json.MarshalIndent`+`fmt.Fprintln`, though it still targets the same `cmd.OutOrStdout()` writer.

`internal/config.Config` (`internal/config/config.go:89-96`) already has a `Debug DebugConfig` field (`:39-42`) defaulting to `false` (`:100-104`), already round-tripping through `.spektacular/config.yaml` (`FromYAMLFile`/`ToYAMLFile`, `:135-152,240-250`) and already covered by tests (`internal/config/config_test.go:15,79`) — but it has zero read-sites anywhere outside its own declaration. This repo's own checked-in `.spektacular/config.yaml` already sets `debug: enabled: true`.

`internal/workflow` persists exactly one shared `.spektacular/state.json` per project (`internal/workflow/state.go:14-21`'s `State{Kind, CurrentStep, CompletedSteps, CreatedAt, UpdatedAt, Data}`, `saveState`/`loadState` at `:35-61`), covering all three workflow kinds (spec/plan/implement) — only one can be in progress at a time, guarded by `cmd/resume.go`'s cross-kind detection. `Workflow.Goto(name)` (`internal/workflow/workflow.go:182-195`) special-cases `name == w.Current()` by calling `renderStep` (`:241-260`), which re-invokes the step's callback without firing any FSM transition and without calling `saveState` — it returns `nil`, identical in shape to a genuine advance. This is independently documented at `.spektacular/knowledge/gotchas/goto-to-current-step-is-a-silent-noop.md` and is the concrete evidence this plan's outcome-detection design (§ below) is built around. Rejected transitions (`fsm.InvalidEventError`/`fsm.UnknownEventError`) and a step's own domain error (`fsm.CanceledError`, from the `before_`-callback wiring landed by plan `000030`'s Phase 3.1) are both distinguishable from a real advance by error type; the silent no-op is not.

`.spektacular/debug/` already exists on disk and is already excluded from version control by the repo root `.gitignore` (`.spektacular/debug/`, under the comment "# Spektacular debug output"), currently holding stale, unrelated JSONL/log content from a dead `internal/runner`-era harness (last touched 2026-03-04–03-06; `internal/runner` itself is unreferenced by any current `cmd`/`internal` code). Nothing in the live codebase writes there today.

No session/run identifier of any kind exists in the codebase (`grep` for `uuid|session_id|SessionID|instance` returns nothing relevant). The closest existing identity is the per-workflow `name` set via `wf.SetData("name", ...)` (e.g. `cmd/spec.go:237`), which identifies a feature instance, not a run, and is absent for non-workflow commands.

## Per-Phase Technical Notes

### Phase 1.1: Build the session record writer

**File changes:**
- New package `internal/sessionlog/` (new directory). New file `internal/sessionlog/record.go`:
  - `Event` struct (reduced for this phase — no `SessionID`/`StateBefore`/`StateAfter`/`Advanced` yet, those are added in Phase 2.1/2.2): `Seq int64`, `Timestamp time.Time`, `Command []string`, `DurationMS int64`, `ExitCode int`, `Response string`. JSON tags snake_case to match the rest of the codebase's wire conventions (compare `internal/output/writer.go:45-52`'s `ErrorResponse` tags).
  - `Record(logPath string, ev Event)` — no return value (per plan's Data Structures & Interfaces § `Recorder`). Opens `logPath` with `os.OpenFile(logPath, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)` (mirrors the mode used by `internal/workflow/state.go:60`'s `os.WriteFile(path, data, 0644)`, minus append since that's a full overwrite not a log), `os.MkdirAll(filepath.Dir(logPath), 0755)` first (mirrors `internal/workflow/state.go:51`), marshals `ev` with `encoding/json`, writes the line + `"\n"`. Every error from any of these steps is swallowed inside this function — nothing is returned, nothing is logged elsewhere, matching the plan's "contained inside this one function" design decision.
  - A package-private, non-persisted sequence counter: since `Record` is called once per process (one CLI invocation = one process = one entry), `Seq` cannot be a simple in-memory incrementing int — it must be derived from the existing line count of `logPath` at call time (read-and-count, or track via a lightweight length probe) so ordering stays correct across process boundaries. Implementer note: counting existing lines by reading the file is simplest and correct for this codebase's invocation-per-process model; do not add a second marker/counter file — that would contradict the plan's Data Structures decision to avoid a session registry.
- New file `internal/sessionlog/record_test.go`: unit tests only, no dependency on `cmd` or `internal/workflow` — construct `Event` values directly and call `Record` against a `t.TempDir()` path, and separately against a deliberately unwritable path (e.g. a directory where a file is expected, or a read-only permission bit) to prove the no-error-return guarantee holds under real failure, not just the happy path.

**Complexity**: Low
**Token estimate**: ~12k
**Agent strategy**: Single agent, sequential execution — small, fully self-contained package with no cross-package coupling; no orchestration needed.

### Phase 1.2: Wire recording into every command, gated by the existing debug option

**File changes:**
- `cmd/root.go:33-40` (`runRoot()`) — the only production touch point for this phase. Extend it to:
  1. Call `loadConfig()` (`cmd/root.go:63-72`, already exists) once at the top; if it errors, treat debug as disabled for this invocation (fail-open per the plan's assumption) rather than surfacing a new error.
  2. If `cfg.Debug.Enabled` is true: capture `argv := os.Args[1:]` and `start := time.Now()`; save the current output writer (`orig := rootCmd.OutOrStdout()`) — **must** read the writer cobra already has, not assume `os.Stdout`, because `cmd/implement_test.go:51-62`'s `setupImplementCmd` already overrides it to a test buffer via `rootCmd.SetOut(stdout)`, and `runRoot()` must compose with that, not bypass it; build `buf := &bytes.Buffer{}` and `rootCmd.SetOut(io.MultiWriter(orig, buf))` for the duration of `Execute()` (and the failure-formatting write, see point 6) only.
  3. Run `err := rootCmd.Execute()` exactly as today (`cmd/root.go:34`).
  4. If debug was enabled, build the reduced `sessionlog.Event{Seq: ..., Timestamp: start, Command: argv, DurationMS: time.Since(start).Milliseconds(), ExitCode: <0 or 1, matching what runRoot already returns>, Response: buf.String()}` and call `sessionlog.Record(logPath, ev)`. `logPath` is `.spektacular/debug/session-log.jsonl`, built the same way `dataDir()` (`cmd/root.go:76-82`) already builds `.spektacular/`'s path — reuse that helper, append `"debug"`/`"session-log.jsonl"`.
  5. **Restore** `rootCmd.SetOut(orig)` only after the whole outcome has been written — i.e. after the failure-formatting write too, not immediately after `Execute()` returns. This matters because the existing failure branch (`output.WriteFailure(rootCmd.OutOrStdout(), toErrorResponse(err), globalFields)`, `cmd/root.go:38`) runs *after* `rootCmd.Execute()` returns, i.e. outside a tee window that ends right at step 3 — the tee must stay installed through that write too, or the recorded `Response` for a failing command would be missing the actual error body. Sequence: tee installed → `Execute()` → (on error) `WriteFailure` through the still-tee'd writer → build and call `sessionlog.Record` (step 4, now correctly capturing the failure body in `buf`) → restore `orig`. Restoration must still happen unconditionally (both success and failure paths) before `runRoot()` returns, since `rootCmd` is a package-level singleton reused across every test case in the `cmd` package's test suite (see `cmd/implement_test.go:51-62`'s `t.Cleanup` resetting `SetOut(nil)`) — leaving the tee installed would leak into unrelated subsequent test cases or subsequent production invocations.
- `cmd/root_test.go` (extend, existing file — `TestWrapper_SuccessAndFailureBothStreamOnStdoutOnly` and siblings already at lines ~88+ per Phase 1.2-of-000030's own test file) — add a new test group in the same style proving: (a) toggle off → no `.spektacular/debug/session-log.jsonl` file is created; (b) toggle on → the file exists and contains one entry per command run, across a success case, a rejected-transition case (e.g. `spec goto` to an unreachable step, mirroring `cmd/error_response_test.go`'s existing `TestGoto_UnreachableStepReturnsActionableError` scenario), and a plain command-level error case; (c) toggle-on vs toggle-off produce byte-identical `stdout`/exit code for the same command, reusing the existing `runRootCmd` helper (`cmd/root_test.go:67-72`) called twice with a config-file fixture toggling `debug.enabled` between the two calls.
- Test fixture note: toggling the config requires writing a `.spektacular/config.yaml` with `debug: enabled: true` into the test's `t.TempDir()` before invoking — follow the existing fixture-writing convention already used elsewhere in this test file (e.g. `writeSpecFileFixture`, `cmd/root_test.go:76-85`) rather than inventing a new one.

**Complexity**: Medium
**Token estimate**: ~28k
**Agent strategy**: Sequential — implement the `runRoot()` change directly (small, precise, single-file, correctness-sensitive around the writer save/restore timing), then delegate the `cmd/root_test.go` additions to a sub-agent following this codebase's own established pattern (plan `000030`'s Phase 1.2 test step delegated its analogous `cmd/root_test.go` wrapper tests the same way). Independently re-run the full suite after the sub-agent's pass, per that same established pattern.

### Phase 2.1: Record whether a command actually advanced anything

**File changes:**
- `internal/sessionlog/record.go` — extend `Event` with `StateBefore *StateSnapshot`, `StateAfter *StateSnapshot`, `Advanced bool`. Add `StateSnapshot` struct: `Kind string`, `Name string`, `CurrentStep string`, `CompletedSteps []string` — field names/shapes deliberately mirror `internal/workflow/state.go:14-21`'s `State` struct (minus `CreatedAt`/`UpdatedAt`/`Data`, which aren't needed for the diff) so a reader familiar with `state.json` recognizes the shape immediately. `internal/sessionlog` still does not import `internal/workflow` (per the plan's Implementation Detail decision) — `StateSnapshot` is `sessionlog`'s own type, built by `cmd` from what it reads.
- `cmd/root.go` — add a small unexported helper, e.g. `readStateSnapshot() *sessionlog.StateSnapshot`, that: builds the state path the same way `internal/workflow`'s own callers do (`dataDir()` at `cmd/root.go:76-82` + `"state.json"`, matching `cmd/spec.go:99-101`'s `stateFilePath` construction — read-only, no new export needed from `internal/workflow`), reads and `json.Unmarshal`s it into an anonymous struct with just `Kind`/`CurrentStep`/`CompletedSteps`/`Data["name"]` (Name lives inside `State.Data`, a `map[string]any`, per `internal/workflow/state.go:20` and `wf.SetData("name", ...)` call sites, e.g. `cmd/spec.go:237`), and returns `nil` if the file does not exist (no workflow has run yet — not an error). Call this once before `rootCmd.Execute()` and once after (within the same debug-enabled branch added in Phase 1.2), and set `Advanced` by comparing the two snapshots — not by inspecting `err`: `Advanced = before/after differ in CurrentStep, len(CompletedSteps), or (both nil-check) Name/Kind`. This is deliberately independent of whatever `err` `rootCmd.Execute()` returned, since the whole point (per research.md's alternative-3 rejection) is that a `nil` error does not imply advancement.
- `cmd/root_test.go` — add a regression test reproducing `.spektacular/knowledge/gotchas/goto-to-current-step-is-a-silent-noop.md`'s exact scenario end-to-end through `runRootCmd`: run `spec new` (lands on `overview`, per that gotcha doc's own example and `internal/workflow/workflow_test.go:100-125`'s equivalent unit-level case), then run `spec goto --data '{"step":"overview"}'` (the currently-active step) with debug enabled, and assert the second recorded entry has `Advanced: false` despite `ExitCode: 0`/no error in its `Response`. Also assert a first-ever command in a brand-new temp dir (no `state.json` yet) records `StateBefore: nil` without error.

**Complexity**: Medium
**Token estimate**: ~20k
**Agent strategy**: Sequential — the diff logic is small but correctness-sensitive (must exactly reproduce the no-op scenario), implement directly; delegate the regression test to a sub-agent once the production shape is settled, independently re-run the full suite after.

### Phase 2.2: Group recorded entries by the piece of work they belong to

**File changes:**
- `internal/sessionlog/record.go` — add `SessionID(state *StateSnapshot) string`, a pure function: `state == nil` (or `Kind`/`Name` both empty) → fixed sentinel `"no-active-workflow"`; otherwise `state.Kind + ":" + state.Name` (matches the plan's Data Structures & Interfaces § `SessionID` decision — no separate registry, no new persisted marker). Add `SessionID string` to `Event`.
- `cmd/root.go` — in the same debug-enabled branch, compute `SessionID(stateAfter)` — **use the *after* snapshot, not before**. Resolved during planning, not deferred: the very first call in a workflow's lifetime (`spec new`/`plan new`/`implement new`) has `stateBefore == nil` (no `state.json` yet) and `stateAfter` holding the new `(Kind, Name)` — it is the one call where before/after legitimately differ. Deriving `SessionID` from `stateBefore` would tag that founding call under the `"no-active-workflow"` sentinel while every later call on the same instance gets `"<kind>:<name>"`, violating the acceptance criterion that every entry for the same piece of work carries the same tag. Deriving it from `stateAfter` tags the founding call consistently with everything that follows, and is identical to `stateBefore` in every other case (a rejected/no-op command changes neither snapshot, so before and after already agree). Set `ev.SessionID` before calling `sessionlog.Record`.
- `cmd/root_test.go` — add a session-isolation test: run two full command sequences in the same `t.TempDir()`/config for two *different* named workflow instances (e.g. two separate `spec new` calls in two separate temp dirs sharing one record file path, or two sequential unrelated `spec new` → `spec goto` chains after each other in the same project — whichever reproduces two distinct `(Kind, Name)` pairs landing in the same `session-log.jsonl`) and assert their entries carry two distinct `SessionID` values with no overlap; and a resume case: `spec new` → (simulate a gap, no special handling needed since nothing time-based is involved) → `spec goto` on the same instance, asserting both entries share the same `SessionID`.

**Complexity**: Low-Medium
**Token estimate**: ~15k
**Agent strategy**: Single agent, sequential execution — small, well-specified addition on top of Phase 2.1's already-built snapshot machinery; the one implementer judgment call (before- vs after-snapshot for `SessionID`) was already resolved during planning (use after-snapshot — see above), not left for the implementer to decide.

## Migration Notes

None. No existing data format changes, no config schema changes, no breaking changes to any existing command's behavior when the toggle is off (the default) or on. Operators who want recording set `debug: enabled: true` in `.spektacular/config.yaml`, a field that already exists and already round-trips today — no migration step is needed for it to take effect once Phase 1.2 lands.

## Performance Considerations

When the debug toggle is off (the default), this plan adds a single boolean check to `runRoot()` and nothing else — no measurable overhead. When enabled, each command does two small file reads (`state.json` before/after, typically a few hundred bytes), one in-memory buffer copy of the response (already-bounded by what the command would have written anyway), and one JSON-line append to `.spektacular/debug/session-log.jsonl`. The one growth-sensitive detail is Phase 1.1's `Seq` derivation (counting existing lines in the record file at write time, per that phase's notes above) — this means each write's cost grows with the record file's size over a long-running, always-on-recording project. This is a known, accepted trade-off (see plan.md § Out of Scope: no retention/rotation policy is in scope) rather than an oversight; if a future project's real-world usage shows this becoming a practical problem, addressing it is future work, not something this plan needs to solve preemptively for a spec whose stated success metric is "left on for as long as an investigation needs it," not indefinite always-on production use.
