# Research: 000036_present-drafts-as-text-not-dialog

## Alternatives considered and rejected

- **Editing every affected step template directly** (~20 files across the spec/plan/implement `templates/steps/*` trees) — rejected: large, repetitive diff; drifts out of sync as new steps are added. (Spec 000036 Technical Approach.)
- **Plan-workflow-only fix** — rejected: the same "draft, then get agreement, without saying how" pattern exists in the spec and implement workflow templates too, not unique to plan.
- **Copying `spec_trigger.go`'s pattern a third time as a new near-identical `review_presentation.go`** — rejected in favor of refactor-first: `memory_context.go` and `spec_trigger.go` are already ~120 lines near-duplicated; a third copy compounds the duplication instead of consolidating it. This was an explicit user choice among three options (refactor-first / copy-as-is / templates-only) made during the spec conversation — refactor-first chosen, and reconfirmed as this plan's Architecture Option C (rejected) during the architecture step.
- **Calling the generic installer directly from each agent's `Install`, with no per-section wrapper functions** (this plan's Architecture Option B) — rejected during the architecture step: `installMemoryContextSection`/`installSpecTriggerSection` are called by name from `claude.go`/`codex.go`/`bob.go` and exercised by name in `memory_context_test.go`/`spec_trigger_test.go`; dropping them would force rewriting all 10 existing tests for no functional gain, conflicting with the spec's behavior-preservation constraint. Resolved: keep thin per-section wrapper functions (this plan's Architecture Option A, chosen).
- **Collapsing `locate*Section`/`append*Section`/`replace*Section` into single generic versions** — evaluated as safe and adopted: this trio is not referenced by name outside its own file, so no external caller or test is affected by collapsing them into `locateManagedSection`/`appendManagedSection`/`replaceManagedSection`.

## Chosen approach — evidence

Refactor to one generic, unexported installer in package `agent` (`installManagedSection`, parameterized by template path + heading + action-noun phrase), backed by generic `locateManagedSection`/`appendManagedSection`/`replaceManagedSection` helpers, all living in a new file `internal/agent/managed_section.go`. The two existing sections become thin wrappers around it; a third new section (`internal/agent/draft_presentation.go`, heading `## Presenting Drafts and Confirmations`, template `templates/agents/draft-presentation.md`) is added as the third caller. Evidence this is safe and mechanical:

- `internal/agent/memory_context.go:25-56` (`installMemoryContextSection`) and `internal/agent/spec_trigger.go:26-57` (`installSpecTriggerSection`) are byte-identical control flow; only the template-path const, heading const, and two hand-written action-noun strings (`"appended Memory & Context section to"` / `"appended Spec-Worthy Discussion Recognition section to"`, `"updated ... section in"` variants) differ.
- `internal/agent/memory_context.go:63-81` (`locateMemoryContextSection`) / `spec_trigger.go:64-82` (`locateSpecTriggerSection`) — 100% identical algorithm, only the heading constant referenced differs.
- `internal/agent/memory_context.go:86-96` / `spec_trigger.go:87-97` (`append*Section`) — 100% byte-identical bodies, no differing tokens.
- `internal/agent/memory_context.go:101-116` / `spec_trigger.go:102-117` (`replace*Section`) — 100% byte-identical bodies.
- `writeAGENTSAtomic` (`memory_context.go:120-130`) and `writeFileAtomic` (`memory_context.go:132-144`) are **already** shared, unexported, defined once in `memory_context.go`, and used by both files plus `claude.go:52,73` (`ensureClaudeImportsAGENTS`, for `CLAUDE.md`, unrelated to the two managed sections but depends on `writeFileAtomic` staying package-visible). Relocating both into `managed_section.go` requires no import or call-site change anywhere, since all are in package `agent`.
- Call sites, identical shape across all three agent surfaces — all call `installMemoryContextSection(projectPath, cfg, out)` then `installSpecTriggerSection(projectPath, cfg, out)`, in that order, against the same `projectPath`/`AGENTS.md`, same `cfg`:
  - `internal/agent/claude.go:25,28` (`claudeAgent.Install`, claude.go:18-32) — order: skills → memory-context → spec-trigger → `ensureClaudeImportsAGENTS` (Claude-only, unrelated to this refactor).
  - `internal/agent/codex.go:17,20` (`codexAgent.Install`, codex.go:13-21) — order: skills → memory-context → spec-trigger (returned directly).
  - `internal/agent/bob.go:20,23` (`bobAgent.Install`, bob.go:13-24) — order: skills → command wrappers (Bob-only) → memory-context → spec-trigger.
  - No agent varies the `AGENTS.md` path or `cfg` shape passed in; all three share one `AGENTS.md` per project. `installDraftPresentationSection` is added immediately after `installSpecTriggerSection` in all three, per this plan's phases step.
- Template structure both existing templates share (`templates/agents/memory-context.md`, `templates/agents/spec-trigger.md`): H2 heading line 1, blank line, 3-line blockquote (`> Managed by ... — edit `templates/agents/<file>.md`... Hand edits will not survive the next init.`), blank line, body prose. The new `draft-presentation.md` template replicates this blockquote contract verbatim, using the `{{command}}` mustache form (matching `spec-trigger.md`'s style, per the architecture step's decision — not `memory-context.md`'s hardcoded-string quirk).
- **Load-bearing quirk, must NOT be "fixed" during refactor**: `templates/agents/memory-context.md:3` hardcodes the literal string `` `spektacular init` `` (no `{{command}}` placeholder), while `templates/agents/spec-trigger.md:3` uses `` `{{command}} init` `` (rendered). This is a deliberate, previously-decided asymmetry (`.spektacular/plans/000023_context-over-memory/plan.md:58`) — the generic installer must still run every template through `mustache.Render(..., map[string]string{"command": cfg.Command})` regardless, and the memory-context template's lack of a placeholder is intentional, not a bug. Confirmed present in the live repo root `AGENTS.md:9` (`spektacular init`, hardcoded) vs `AGENTS.md:24` (`go run . init`, rendered from this repo's `cfg.Command = "go run ."`).
- Repo-root `AGENTS.md` (52 lines, read directly) is the exact byte-for-byte ground truth a behavior-preserving refactor must reproduce when re-run against it with `cfg.Command = "go run ."`: re-running must be a no-op (idempotent), and the new third section's call must append after `## Spec-Worthy Discussion Recognition` (natural insertion order = call-site order, i.e. append after `installSpecTriggerSection` in each agent's `Install`).
- The heading-boundary scan (`locate*Section`) stops at any line whose trimmed form starts with `"# "` or `"## "` — this already correctly stops at the tessl-managed block's own `# Agent Rules <!-- tessl-managed -->` H1 (`AGENTS.md:3`), which is why both existing test files seed fixtures with that literal tessl block as prior content (`memory_context_test.go:47`, `spec_trigger_test.go:47`) — any new tests for the third section, and the generic installer's own tests, should keep this convention. The tessl block (`.tessl/RULES.md`) is a distinct, unrelated third-party mechanism (HTML-comment marker, H1, owned by `tessl install`) — not part of this refactor, noted only so the boundary logic isn't second-guessed.
