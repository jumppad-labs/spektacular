# Feature: Specs and plans as historical artifacts

## What was built

Agents working in a Spektacular-initialized repository now automatically treat every file under `.spektacular/specs/` and `.spektacular/plans/` as a historical, archaeological record — a snapshot of *why* a past change was proposed and what its author intended at that moment, not a description of what the codebase does today. The rule is delivered as instruction prose on two coordinated surfaces:

1. A new `spektacular init`-managed section in `AGENTS.md` — `## Historical Artifacts: Specs and Plans as Archaeology` — that states the rule, the archaeology-on-user-intent exception, and the owning-workflow-live-artifact exception in full. The section is the third instance of the same triad pattern already used for `Memory & Context` and `Spec-Worthy Discussion Recognition`: a Markdown template under `templates/agents/`, a Go installer in `internal/agent/` with locate/append/replace helpers reusing the shared atomic writer, and a one-line wire-in inside each supported agent's `Install()` method (Claude, Bob, Codex). The installer is byte-idempotent — re-running `spektacular init` any number of times converges on a single copy of the section without duplicating headings or disturbing unrelated content — and this is enforced by a six-case unit-test set mirroring the existing installer test shape, including a cross-agent idempotency test that exercises all three registered agents' real install paths.
2. Two prose-only clarifiers in existing step templates that used to look like they contradicted the new rule. `templates/steps/plan/02-discovery.md`'s "Prior research" bullet now opens by framing the reads of prior plans and specs as historical archaeology in service of new-plan research, not as current-state discovery. `templates/steps/implement/01-read_plan.md`'s first-read instruction now opens by acknowledging that the plan documents are the implement workflow's own live artifact — the owning-workflow exception the `AGENTS.md` rule explicitly permits — before the existing "read them through the plan store" instruction.

The rule reaches every session because `CLAUDE.md` at the repo root already imports `AGENTS.md` via `@AGENTS.md`, so a fresh agent session picks up the rule without any user prompt. The rule binds ad-hoc questions, unrelated skills, and general exploration — not only workflow-step contexts — and it is enforced purely at the agent-instruction level per the spec's explicit constraint, with no filesystem-level or tool-level access blocks that would break the archaeology exception.

**Documentation follow-up**: the "process document, not product document" concept introduced by this change — that specs and plans describe the *process* by which a change was proposed and reasoned about, not the *product* that shipped — should also be added to the user-facing website documentation in a future update. Only the changelog note flagging the concept lands with this feature; the website documentation change itself is deferred to a follow-up and is not tracked by this changelog entry beyond this callout.

## Why it matters / what it enables

Before this change, agents treated specs and plans as if they were part of the current-state documentation of the codebase. When asked how a shipped feature currently works, they would often reach for the relevant spec or plan and cite it as authoritative — which produced answers that drifted from reality whenever the shipped code had reshaped or abandoned parts of the original intent. Users had to remind agents mid-session that these documents were archaeological records, not current-state docs, and correct citations that pointed at intent rather than at the code that shipped.

This feature closes that gap durably. Agents now ground current-state answers in source code, tests, and configuration; they only read specs and plans when the user asks a genuinely historical question ("why was X built this way?"); and while a spec, plan, or implement workflow is actively running, the workflow keeps full read/write access to its own live artifact through the dedicated CLI. Users no longer have to restate the rule in each session, and the answers they get about existing features stay aligned with the shipped code — the archaeological source is reached for only when a human is genuinely investigating past intent.

## Deviations from the plan

The plan originally split Phase 1.1 (author template, installer, and tests) from Phase 1.2 (wire the installer into the three registered agents) as two separate implement iterations. During Phase 1.1's `test` step, the six-case test set — mirrored from the existing installer tests — turned out to include a cross-agent idempotency test that cannot pass until the installer is actually wired into `claude.go`, `bob.go`, and `codex.go`. Since Phase 1.1's own acceptance criterion requires "the six-case unit test set is present and **green**", the two phases were co-landed in a single implement iteration under Auto Mode: the template, installer, tests, and wire-in were all written before advancing to `verify`, and both phases' checkboxes were ticked in the same `update_plan` write. Both phases' changelog entries were written separately at that iteration's `update_changelog` step to preserve the phase-by-phase audit log.

Phase 3.1 landed as intended: no code changes were made in the phase itself, because its output — the "process document, not product document" website-documentation follow-up note — is prose content authored by the `update_feature_changelog` step (this one) rather than by a per-phase edit. At Phase 3.1's `update_plan` step, only the phase's own `#### - [x] Phase 3.1:` heading was ticked; the three per-AC checkboxes were left `- [ ]` because at that moment the changelog artifact this entry describes did not yet exist, and ticking them would have violated the "only tick if verified" invariant.

Aside from those two coordination points, no phase deviated from its plan-time description. `make test` and `make lint` were green after every phase's verification pass.
