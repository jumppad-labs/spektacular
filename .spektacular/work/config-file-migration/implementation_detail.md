The migration follows Spektacular's existing command extension pattern: version check gains detection logic that runs before returning its result, similar to how other commands layer validation or enrichment atop their core operation. Detection is a pure function that compares file presence (config.yaml exists, repo.yaml does not) and returns a boolean, keeping the version check's existing flow intact while adding the migration branch.

The project scanner introduces a new pattern for inferring repository metadata from filesystem artifacts. It walks the project root once, collecting evidence (README.md content, build file presence, directory structure), then applies heuristics to produce suggested values. This scanner is deliberately separate from the migration executor, making it testable in isolation and reusable if future features need similar inference. The scanner returns a result struct, never writes files itself, and always succeeds (returning defaults when evidence is missing).

Migration execution follows an atomic transaction pattern: backup first (rename config.yaml to config.yaml.old), then write both new files (repo.yaml and updated config.yaml), with explicit rollback on any failure. The rollback removes both new files and restores the backup, ensuring users never end up with a partially-migrated state. This mirrors the init command's file-writing sequence but adds the backup/rollback layer that init doesn't need.

Existing config serialization patterns are reused without modification. The migration executor calls `Config.ToYAMLFile()` and `RepoConfig.ToYAMLFile()` exactly as init does, and the version check's structured output format gains an optional migration prompt field rather than introducing a new response shape. This keeps the migration's code footprint small and its behavior consistent with established patterns.
